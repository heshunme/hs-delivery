# Destination host acceptance

Use this for a later real-host trial, including when the user owns that acceptance. Local tests exercise helpers and fixture protocols; these scenarios establish the destination host's actual discovery, completion and recovery behavior. This checklist starts unexecuted.

Use a disposable project/task and the actual installed skill. Record machine/OS, host and CLI versions, skill commit, interpreter/dependencies, instruction source and chosen completion mechanism. Keep initialization observations in the local setup receipt and task acceptance in the actual trial record. Initialization cases do not require a sample active task. Use real participant IDs from this task only. Run remote or externally mutating scenarios only within the trial's actual authorization.

| Scenario | Observable acceptance |
|---|---|
| Missing or partial setup | Invocation inspects and previews concrete changes; existing authorization is carried forward, actual gaps require confirmation, and equivalent records/rules are preserved |
| Delivery policy setup | Derivable facts and settled decisions are recovered; uncovered behavior uses applicable defaults. Real conflicts/gaps are presented together with effects and impact/owner, not every blank field. Installed tools do not imply policy completion |
| Local exclusion and worktrees | The actual Git exclusion path is resolved, artifacts are effectively ignored, `.gitignore` is unchanged, tracked artifacts remain tracked and linked-worktree scope is reported |
| Python capability selection | Markdown/core use installs no unnecessary packages; any selected queue environment matches requirements and all relevant launchers use its explicit interpreter; unavailable capabilities stay visible |
| Repeat setup or partial failure | A second adoption reuses complete setup; only relevant gaps are proposed, completed steps are recorded and repair/removal touches only setup-owned changes |
| Fresh start | The host reads existing repository rules and the installed recovery pointer; it finds the intended project conventions and task |
| Compaction/resume | In the first useful actions after each tested transition, the coordinator reloads the skill and current card, retaining the actual candidate, pending work and scope |
| Normal result continuation | Within valid context, the coordinator consumes the result/delta and relevant evidence without reloading all rules or auditing every historical artifact; scoped checks disclose omissions |
| Task selection and execution context | Multiple tasks do not cause newest-card selection; subdirectory/worktree entry resolves the intended task, paused work stays paused and subagent loading is checked separately when used |
| One work round | A writer returns immutable versioned evidence; an independent reviewer inspects the actual candidate and its result reaches the assigned coordinator |
| Finding treatment | A minor-only review does not automatically launch repairs; a proven blocker cannot be deferred while claiming completion; missing evidence stays distinct from a proven defect |
| Project repair policy | A verified blocker fix under an explicit writer-verification-only policy does not force independent recheck, and the final record preserves the earlier reviewed SHA and unreviewed fix delta |
| Review convergence | Incremental rounds preserve prior dispositions and scope. A third completed round with unresolved blockers stops automatic repair/review dispatch, reports progress and next owner, and does not claim success or reset on resumption |
| Review units | Predeclared independent units keep separate finite budgets and explicit interaction coverage; an exhausted unit cannot acquire more rounds through renaming or a retroactive split |
| Mixed artifacts | Review accounts for handwritten, generated and non-text changes with suitable methods and disclosed limits; acceptance uses actual trigger-to-result paths without requiring absent UI/service layers |
| Acceptance proportionality | A one-off observable check can remain manual with evidence; worthwhile automation batches actions. Measurements preserve relevant conditions without requiring unrelated UI/network fields |
| Expanding verification | A measurement/tooling expansion returns to the required delivery conclusion; engineering initial values do not become hard requirements, and prior failures remain visible |
| Candidate and endpoint | Changed configuration/data/artifacts prompt evidence reassessment even at the same SHA; the recorded endpoint may be a PR/MR, artifact or deployment stage and does not imply authority for later stages |
| Busy feedback | Feedback follows the host's supported path without replacing useful work; a feedback-dependent step waits at the named checkpoint |
| Completion while idle | The chosen supported path wakes the coordinator, or the recorded explicit-resumption path is used; no unsupported automatic wakeup is claimed |
| Background success/failure | An authorized long command or existing CI wait retains its actual exit, candidate/run identity and log; the callback leads to correct reconciliation |
| Missing result/interruption | A worker ending before publication or a deliberately interrupted task remains visible as pending; resume inspects existing artifacts before repeating work |
| Observer reconciliation | A processed result, an old watching status and a removed terminal remain separate observations; no process/CI success is inferred from resource removal |
| Drained coordinator route | After actual publishers drain and the old consumer releases ownership, rebind retains results/ACKs/resources, rejects stale state or paused/closed mode, and a real result reaches the new consumer only |
| Duplicate host completion | Test both result/finished orders while active and waiting, including failure without publication; distinguish local duplicate consumption from whether the host still interrupts the turn |
| Stop and cleanup | A pre-stopped command does not launch; a running owned command stops through its supported path; processes and host resources are reconciled |
| Closeout | Current review/gates/findings agree with the card; inbox results are disposed of and owned temporary resources are accounted for |

Save a per-trial copy of the results table under the task's acceptance records; this file stays a reusable checklist. Mark each row passed, failed, pending or inapplicable with a reason and evidence. A queue-specific row may be inapplicable to a native hand-back path. Use a separate binding and evidence for each host actually tested; success on one does not establish another host's behavior.

Retain failures with their environment and version, then append fix/retest evidence. Do not claim the checklist passed merely because local tests or format checks passed. A later host trial can finish the pending acceptance without rerunning unchanged local checks.
